# 常见问题

## 为什么不用 LangChain？

因为这个项目的目的是理解 agent 的本质，不是学会用某个库。整个核心循环只有一百多行，读完你就知道框架在替你做了什么。等能手写循环之后，再去看框架效率会高得多——否则你只是在学它的 API。

## 为什么记忆要把工具调用的往返记录一起存？

模型是无状态的，它每一步能看到什么，完全取决于你传给它的消息数组。如果只保存"用户问了什么、助手答了什么"，把工具调用那段丢掉，恢复之后模型会不记得自己查过什么，可能重复调同一个工具。这个 bug 在真实开发中抓到过：单次模式下完全看不出来，多轮对话里就表现为"它不记得自己刚说过什么"。

## 为什么工具结果里要把 .env 过滤掉？

因为工具的结果最终会发给模型接口，等于发给第三方服务。`.env` 这样的文件名本身就在暴露"这个目录里存着秘密"，所以连名字都不该出现。将来如果加了"读文件内容"的工具，这个过滤必须同步做，否则密钥会被原样读出来发给第三方。

## 为什么部署时要加 --experimental-strip-types？

因为 TypeScript 的类型擦除在 Node 22.18 才默认开启。低于这个版本直接运行 .ts 文件会报 `ERR_UNKNOWN_FILE_EXTENSION`。本机开发用的 Node 版本可能比部署环境高，这种版本差异会造成典型的"本地能跑、线上报错"。

## 为什么检索用关键词而不是向量？

向量检索需要 embedding 模型和向量存储，引入依赖，而且结果不可复现——同样的输入两次算出来的向量可能有细微差别，测试就写不了断言。关键词检索是纯本地计算，结果完全确定。在几十篇文档的规模下，效果差距并没有大到值得为它引入这些麻烦。

## agent 一定会停下来吗？

不会天然保证。所以代码里有 `maxSteps` 上限，跑满了会明确返回"任务未完成"，而不是假装给了一个答案。把未完成伪装成完成，比直接报错危险得多——用户会以为拿到了结论。

## 为什么错误要喂回模型，而不是直接中断？

模型可能编出不存在的工具名，工具也可能执行失败（比如目录不存在）。把这些当成"工具返回的错误"喂回去，模型有机会自己纠正；直接中断的话，一次意外就毁掉整轮对话。这是 agent 和普通脚本最大的心态差别：错误是给模型的输入，不是程序的终点。
