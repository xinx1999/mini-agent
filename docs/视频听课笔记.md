## 1. 四个视频的实测目录（含我的取舍判断）

> **播放量是 2026-10-14 实测的，不是学习路线里的旧数字。** 四个视频里有**两个的数字很难看**，
> 这件事本身比目录更重要，先看下面这一条：

### ⚠️ 先说一个筛选标准失效的问题

学习路线附录 A 里写的筛选逻辑是：**「播放量高 = 质量经过大量人验证，
比播放量 1000-2000 的新视频可靠」**。但我实测了实时播放量：

| 视频 | 实测播放 | 发布日 | 距今 |
|---|---|---|---|
| 黑马·RAG与Agent | **372.6 万** | 2026-01-21 | 9 个月 |
| 尚硅谷·LangGraph | **78.0 万** | 2026-07-15 | 3 个月 |
| RAG 系统性教程 | **1,536** | 2026-10-07 | **7 天** |
| FastAPI 完整实战 | **2,012** | 2026-10-06 | **8 天** |

**后两个视频，恰好就是学习路线里被判定为"不可靠"的那一类**——发布一周、播放量 1000-2000。

这不等于它们讲得差（分P 目录看着很全、很对口），而是说：
**「播放量」这个质量信号在这两个视频上完全没有生效**，它们是新视频，还没被市场验证过。
原来的判断"质量经过大量人验证"对它们**不成立**。

**建议的处理方式**：
- 黑马 + 尚硅谷 → 有数据背书，可以放心按计划看；
- RAG 教程 + FastAPI → **先试看 1-2P**（比如 RAG 的 P01、FastAPI 的 P04），
  用学习路线里那个标准自己判断：「它讲不讲为什么？还是只是 API 说明书？」
  讲得好就继续，讲得不好就换——**别因为是"路线里指定的"就硬看**。

## 3. 核心概念速记（我整理的，不是视频原话）

> 这一节是给面试口述用的。每条都压缩成"能一口气说完"的长度。

**LangChain 五大组件**
Models（模型）/ Prompts（提示词模板）/ Chains（编排）/ Memory（记忆）/ Tools & Agents（工具与智能体）。
你项目一一对应：`llm.ts` / system prompt / `agent.ts` / `memory.ts` / `tools.ts`。

**LCEL**
用 `|` 把组件串成管道，靠的是所有组件都实现了 `Runnable` 接口（有 `invoke`/`stream`/`batch`）。
`prompt | model | parser` 就是一条链。**它的价值是统一了"可组合"的协议。**

**Chain vs Agent（必考）**
Chain 是**固定流程**，路径写死；Agent 是**动态决策**，由模型自己决定调哪个工具、调几次。
你项目是纯 Agent（`for` 循环），所以回答时可以直接说"我手写的那个循环就是 Agent 的最小形态"。

**ReAct**
Reasoning + Acting 交替：想一步 → 做一步 → 看结果 → 再想。对应你循环里的
"调模型 → 拿到 tool_calls → 执行 → 把结果塞回 messages"。

**Function Calling / Tool Calling**
模型不执行工具，它只**输出一个结构化的调用请求**（工具名 + 参数 JSON），
执行永远是你的代码做的事。你 `llm.ts` 里按 index 拼 `tool_calls.arguments` 就是这件事的细节。

**RAG 的本质（高手答法）**
把外部知识引入推理过程的**架构**：不改模型参数，而是在推理时检索相关知识，
提升准确性、实时性和可追溯性。不是"向量数据库 + 大模型"这种流程描述。

**什么时候不该用 RAG**
知识相对固定且对延迟极敏感 → 可能微调或长上下文更合适；
数据量极小（几十条）→ 直接塞进 prompt，上检索是过度设计。

**混合检索 / 多路召回 / Rerank 的区别**
- 多路召回：同时用多条通道（关键词 BM25 + 向量）各召回一批；
- 混合检索：把多路结果**融合**成一个排序（RRF 之类）；
- Rerank：对融合后的候选做**精排**（交叉编码器，慢但准），取 Top-K 给模型。

**Embedding vs 关键词**
关键词（你现在的 TF-IDF）靠字面重合，**同义词/改写就检索不到**；
向量靠语义距离，**能召回字面不同但意思相近的内容**，代价是可能引入语义漂移。
所以工程上通常是两者都要。

**Evals（高频挂点）**
面试官问"你怎么知道 agent 改好了还是改坏了"。你的答案：
> 确定性的部分用断言（我项目里有 142 条），非确定性的部分用黄金问题集——
> 每次改动跑一遍，看命中率和回归情况。

**RAG 评估指标**
检索侧：命中率 / Recall@K / MRR；生成侧：忠实度（faithfulness，有没有编）/
相关性 / 答案正确性。工具：RAGAs、TruLens。

**向量数据库选型**
- Chroma：本地开发、开箱即用；
- pgvector：已有 Postgres、想少引入一个组件；
- Milvus / Qdrant：数据量大、要生产级性能和水平扩展。
索引：HNSW（图，快，内存占用高）是默认选择；IVF 类要先聚类、适合超大规模。

**LangGraph 和 LangChain 的区别**
LangChain 是**组件库 + 链式编排**；LangGraph 把流程建模成**显式状态机**
（StateGraph：节点 + 边 + 条件分支 + 循环），适合需要回退、分支、多 Agent 协作的场景。
一句话：**LangChain 管"单个链怎么搭"，LangGraph 管"多个步骤怎么流转"**。
